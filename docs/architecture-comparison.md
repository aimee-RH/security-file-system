# 架构对比：学城 vs 不可信存储加密文件系统

> 文档日期：2026-08-17
> 对比来源：学城架构文档 12.3 数据访问与一致性、12.4 权限计算架构
> 本地参考：`/Users/gaoruihuan/docs/学城-共享文档与知识库管理机制-20260814.md`
> 项目根：`/Users/gaoruihuan/security-file-system`

## 一、对比的目的

学城是服务端可信的生产系统，本项目是服务端不可信的加密文件系统。两者用相似机制（stepVersion、权限继承、5 级权限）解决不同问题，**模型层面的权衡**比功能差异更值得讲清楚。

简历叙事核心：**模型差异决定设计权衡**，不是功能缺失。

## 二、12.3 数据访问与一致性——学城模型

学城按数据类别分写/读路径 + 一致性级别：

| 数据类别 | 写入路径 | 读路径 | 一致性 |
|---|---|---|---|
| 文档正文（PM JSON） | 协作服务直写主库 | WebSocket 增量 + 全量回源 | 强一致（stepVersion 串行） |
| 文档元信息 | 主服务 → 主库 | 直读 + 缓存 | 强一致 |
| 权限 | 权限服务 → citadel_perm | 多方读 + 缓存 | 最终一致（缓存失效重算） |
| 草稿 | 草稿服务 → citadel_draft | 客户端拉取 | 最终一致 |
| 评论/点赞 | 反馈服务 → citadel_comment | 直读 | 最终一致 |
| 历史版本 | 协作服务异步写 → citadel_history | 异步读 + 分页 | 最终一致 |
| 搜索索引 | MQ → ES | ES 查询 | 最终一致（秒级延迟） |
| 通知 | MQ → 通知服务 | 大象 + 站内 | 最终一致 |

**核心/非核心集群分离**：
- 核心 `citadel`：写密集 + 强一致（文档/权限/附件元数据）
- 非核心 `citadel_normal`：高吞吐读 + 可容忍延迟（统计/历史/通知/搜索）
- **统计类高频聚合查询会锁表**，独立集群避免打挂核心写入

## 三、12.4 权限计算架构——学城模型

权限服务是多方依赖的基础组件：

```
权限请求 → 权限服务
  ├── 加载节点权限树（缓存）
  │     ├── 自身权限记录 (doc_perm)
  │     ├── 父链权限继承（递归向上）
  │     └── 空间默认权限 (space_perm)
  ├── 多维度解析（部门/个人/大象群/邮件组）
  │     └── 邮件组 2h 同步 → 容忍 2h 延迟
  ├── 计算最终权限（取并集，5 级取最高）
  └── 返回 effective permission
       ↓
调用方：目录树 / 搜索 / CLI
```

**继承 5 个关键点**：
1. 子节点默认继承父节点权限，递归到空间根
2. 子节点单设权限 → "切回独立"，停止向上递归
3. "移除继承" = 强制停止向上递归（即使没单设权限）
4. "恢复继承" = 重新允许递归
5. 移动文档 → 继承链重算，单设权限记录保留

**性能优化**：`(user_id, doc_id)` 缓存；失效触发=权限变更/文档移动/用户离职；邮件组 2h 同步做缓存 TTL 兜底。

## 四、本项目实现对照

### 4.1 数据访问与一致性对照

| 学城数据类别 | 本项目实现 | 一致性 | 差距 |
|---|---|---|---|
| 文档正文 | `FileChunk` 链表 + AES 加密 | 强一致（per-UUID mutex 串行） | ✅ 对齐 |
| 文档元信息 | `FileMetadata`（owner/fileName/version） | 强一致 | ✅ 对齐 |
| 权限 | `Directory.Permissions` + `ShareEntry` in `SignedShareList` | **强一致**（无缓存） | ⚠️ 学城最终一致 |

| 评论/点赞 | ❌ 无 | — | gap |
| 历史版本 | ❌ **撤销时全删** | — | 设计权衡（见 §6） |
| 搜索索引 | ❌ 无 | — | gap（可搜索加密是研究课题） |
| 通知 | `NotifyStore` in-memory | 最终一致 | ✅ 对齐 |

### 4.2 权限计算对照

| 学城维度 | 本项目实现 | 状态 |
|---|---|---|
| 权限服务独立（多方调用） | `client/directory.go` 内嵌 | ❌ 未独立 |

## 五、根本差异：模型层面

### 5.1 存储可信模型

| 维度 | 学城 | 本项目 |
|------|------|--------|
| 存储可信模型 | 服务端可信 | 服务端不可信 |
| 权限执行 | 服务端运行时检查 | 密码学层强制（撤销 = 全密钥重生） |
| 一致性策略 | 混合（核心强一致 + 非核心最终一致） | 单一强一致 |
| 性能优化 | 缓存 + 集群分离 | 无（不可信存储下缓存需密码学保护） |
| 历史版本 | 异步归档 + 分页读 | 撤销时强制删除（前向保密代价） |

### 5.2 模型差异决定的设计权衡

学城服务端可信 → 可以：
- 缓存权限计算结果（服务端缓存不可被外部篡改）
- 保留历史版本（服务端权限检查就能阻止未授权访问）
- 核心非核心集群分离（服务端控制数据分布）

本项目服务端不可信 → 必须放弃：
- **缓存需密码学保护**：缓存条目带 HMAC 签名，否则攻击者把"无权限"改成"有权限"
- **历史 chunk 必须删除**：否则被撤销用户用旧 key 仍可解（前向保密破坏）
- **不能集群分离**：所有数据在不可信存储上，分布反而扩大攻击面

**这是模型层面的权衡，不是功能缺失。**

## 六、3 个关键差异深度分析

### 6.1 一致性策略——学城混合 vs 本项目单一强一致

学城**故意**让权限/搜索/通知最终一致，强一致只留给核心写入。高 QPS 读（目录树过滤、搜索）走缓存不压主库。

本项目所有读写都强一致（Datastore 直读直写，无缓存层），如果 QPS 上来：
- 权限检查每次都 `LoadDirectory + ResolvePermission` 递归——递归到根目录可能 5+ 次 DatastoreGet
- 没有 `(user_id, doc_id)` 维度缓存，每次访问都全量计算

**叙事**：不要把"强一致"说成设计目标，要承认"无缓存层是已知限制，升级路径是学城的最终一致 + 缓存"。

### 6.2 历史版本归档——撤销时全删 vs 异步保留

学城协作服务异步写 `citadel_history`，旧版本可分页读。

本项目 `RevokeAccess` 流程第 7 步（`client/revoke.go:348-372`）：**删除旧 chunk 链 + 旧 metadata**。这是前向保密的必要条件（被撤销用户不能持有旧 chunk 副本），代价是**丢失历史版本**。

学城可以查"昨天 14:00 这个文档是什么内容"，本项目不行。

**这是设计权衡，不是缺陷**：
- 学城：服务端可信，旧版本可保留（内部作恶风险低）
- 本项目：服务端不可信，旧 chunk 必须删（否则被撤销用户用旧 key 仍可解）

**简历亮点**：不可信存储模型下，撤销必须删除历史 chunk 实现前向保密，代价是放弃版本历史；学城等服务端可信系统靠权限控制而非数据删除。这是**模型层面的差异**，比"我没做历史版本"高一个层次。

### 6.3 权限缓存——不可信存储下的额外挑战

学城按 `(user_id, doc_id)` 缓存权限计算结果，失效触发=权限变更/文档移动/用户离职。

本项目 `ResolvePermission` 每次都全量递归：
- 加载 Directory → 遍历 Permissions → 不匹配则递归到父目录 → 再加载 → 再遍历...
- 深度 N 的目录树，最坏 N 次 DatastoreGet + N 次解密

**不可信存储下缓存的额外挑战**：
- 缓存放客户端还是服务端？服务端缓存可被攻击者篡改（不可信存储）
- 学城服务端可信所以缓存没问题，本项目的缓存需要密码学保护（缓存条目带 HMAC），否则攻击者把"无权限"改成"有权限"

**叙事**：不可信存储模型下，性能优化手段（缓存）需要密码学保护——这是学城不需要考虑的额外维度。

### 6.4 撤销机制——BFS 显式遍历 vs 权限继承断开

学城撤销靠**目录树权限继承**（12.4 模式）：
1. 删除该用户在该文件的权限条目（`doc_perm` 表删一行）
2. 权限缓存失效（`(user_id, doc_id)` 缓存条目删除）
3. 下游用户的权限自动失效——因为他们继承自被撤销用户（子节点没单设权限时继承链断开）

本项目 `RevokeAccess` 走**完全不同的路径**：
1. BFS 显式遍历 `SignedShareList` 共享图，找出所有下游被撤销用户
2. 全密钥重生（`fileEncKey` / `fileHMACKey` / `metadataEncKey` / `metadataHMACKey`）
3. 重新加密所有 chunk（不是只加密新 chunk，是全部重写）
4. 生成新 metadata UUID + 新 ShareList
5. 更新保留用户的 FileView 指向新 metadata
6. 删除旧 chunk 链 + 旧 ShareList + 旧 metadata
7. 通知所有被撤销用户 + 保留用户

**关键差异表**：

| 维度 | 学城 | 本项目 |
|------|------|--------|
| 撤销执行 | 服务端权限条目删除 | 密码学层重置（密钥重生 + chunk 删除） |
| 传播机制 | 权限继承链自动断开 | BFS 显式遍历共享图 |
| 下游处理 | 继承失效（子节点继承不到权限） | 递归撤销（BFS 找出所有下游） |
| 旧数据 | 保留（服务端持明文） | **强制删除**（前向保密要求） |
| 信任模型 | 服务端可信 | 不可信存储 |
| 性能 | O(1) 删权限条目 + 缓存失效 | O(共享树大小) + 重新加密全部 chunk |
| 安全强度 | 服务端被攻破则全暴露 | 存储全部泄露，旧密钥也解不了新 chunk |

**为什么撤销不用继承？**

继承模型依赖**服务端可信**——服务端权限检查时继承链断开就拒绝访问。但不可信存储下：
- 攻击者（或被撤销用户）可能持有旧 chunk 副本 + 旧密钥
- 即使权限检查拒绝，他绕过权限系统直接用旧密钥解旧 chunk 仍然能读
- 必须密钥重生：让旧密钥失效（HMAC mismatch）
- 必须删旧 chunk：让旧密钥无数据可解（前向保密）

**继承只能"拒绝访问"，不能"让旧密钥失效"**——这是不可信存储 vs 服务端可信模型的根本差异。

**本项目两套机制并存**：

| 机制 | 用途 | 阶段 | 模式来源 |
|------|------|------|---------|
| `Directory.ResolvePermission` 递归继承 | 权限**检查** | 访问时 | 学城 12.4 |
| `RevokeAccess` BFS + 全密钥重生 | 权限**撤销** | 撤销时 | 不可信存储模型 |

两套机制互不相关：继承是静态权限模型（"该用户有没有权限"），RevokeAccess 是动态撤销执行（"该用户失去权限后，密码学层怎么保证他真的访问不到"）。

## 七、本项目比学城"强"的地方

1. **撤销前向保密**：学城做不到（服务端持明文），本项目核心差异化
2. **chunk swap 防御**：HMAC 含 UUID（`client/store.go:55-67`），学城不需要（服务端鉴权）
3. **conflated chunk 防御**：每文件独立 key，学城不需要
4. **invitation 重放防御**：撤销即删除（`client/revoke.go:96`），学城有类似机制但路径不同

测试支撑：`client/threat_model_test.go` 6 个测试全 PASS。

## 八、本项目比学城"弱"的地方（坦诚承认）

1. **无缓存层**：每次权限计算全量递归
2. **无核心/非核心集群分离**：单 Datastore
3. **无历史版本**：撤销强制删除（前向保密代价，但也是设计选择）
4. **权限服务未独立**：内嵌在 client 包
5. **无多方调用场景**：没有目录树/搜索/CLI 三方共享权限服务
6. **多维度主体未落地**：group/dept 结构在但没实现
7. **无 OT 协同**：append 串行化而非 rebase
8. **无草稿/评论/点赞**：场景外的功能
